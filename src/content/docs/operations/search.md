`/search` is the site's main browse and search page. Since 2026-10-29 it is served by
**`sacda_fast_search`**, a JSON search API plus a Svelte front end, instead of the stock
Search API view. The old view still exists at `/search-legacy`. The module is also
published on its own as `isle-fast-search`.

## Why it was rebuilt

PROD went down repeatedly when crawlers walked facet combinations (see the
[Incident log](/docs/operations/incident-log/)). Profiling on DEV showed:

- Solr was never the problem: 2 to 4 ms per query.
- Each uncached `/search` request cost about **0.13 CPU-seconds of Drupal page building**
  (view, facet blocks, render arrays, Twig), and much more on PROD's larger index.
- PROD has 2 CPUs and 5 php-fpm workers, so a crawler could occupy the whole machine.

Things that were tried and **did not help**: more php-fpm workers (3, 5 and 8 all
saturated the same way), lower facet hard limits, disabling the view's tag cache, a
bigger Solr heap, and patching facet processors (an apparent hotspot turned out to be a
profiler artifact).

## How it works now

| Piece | What it does |
|---|---|
| `/api/search` | Runs the same Search API query as the view, then fetches titles, parents and models with flat SQL instead of loading entities. About 0.024 CPU-seconds per request on DEV. Cacheable per query string |
| `/search` page | Drupal renders the view's page template, regions and blocks once. The four blocks the app owns (advanced search, pager, results, facets) become mount points |
| Static shell | `drush sacda-fast-search:shell` writes that rendered page to `/var/www/drupal/search-shell`. The `exhibits` nginx serves it to every anonymous `GET /search`, whatever the facets, with **no PHP at all**. Logged-in users (session cookie) still get the live page |
| Stored thumbnails | `sacda_modules` keeps a `sacda_thumbnail` table of collection thumbnails, so results don't walk children to find one |

The app reads facet order, soft limits, labels, sorts and pager settings from Drupal
config, so changing a facet in the UI changes the page. Facet values beyond the soft limit
are fetched only on "Show more", which keeps responses small (PROD has about 8,000 facet
values). Facets with more than five values have a filter box.

Measured on DEV with the same multi-facet crawl at 10 requests a second: the old view
used 1.25 of 2 cores, the API 0.22. Maximum throughput went from 11 to 47 requests a
second.

Deliberate differences from the old view: "or … is not" rows work (they 500 on the old
view), a two-row results header on phones, and no highlighted excerpts.

## Operating it

The shell is regenerated by `make deploy` (and on Drupal cron once the module is deployed). To regenerate it by hand:

```bash
docker compose exec -T drupal drush sacda-fast-search:shell
```

Rebuild stored thumbnails after a big ingest (otherwise the first visitor pays for it):

```bash
docker compose exec -T drupal drush sacda:thumbnails:rebuild
```

Saving a node or media clears its ancestors' rows automatically. To switch stored
thumbnails off without a deploy, set `$settings['sacda_image_discovery_cache'] = FALSE;`
in `settings.php`.

If the shell file is missing, nginx passes `/search` to Drupal instead of returning 404.
That is safe for correctness but expensive under a crawl, which is why the temporary
`search-page` rate limit exists. See [Traefik and rate limits](/docs/operations/traefik-and-rate-limits/).

## Changing the UI

The Svelte source is in `web/modules/custom/sacda_fast_search/ui`. CI builds it from
source and ships only `dist/`. Locally:

```bash
cd web/modules/custom/sacda_fast_search/ui
bun install
bun run build
```

Then regenerate the shell so anonymous visitors get the new build.

## If Nginx tuning becomes possible

The campus proxy is not ours, and PROD's in-container nginx is generated by the image.
A second layer was designed and validated for the PHP 8.3 image: a shared search budget
returning 429 beyond it, and a dedicated 2-worker php-fpm pool for search. The files are
in `scripts/performance/prod-buildkit6/` in `isle`. Use a queue (`burst` without
`nodelay`) at 6 to 8 requests a second, so people wait briefly instead of getting 429s.
